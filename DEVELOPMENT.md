# WhoDoesWhat — implementation reference

Detailed implementation notes for contributors. For the user-facing overview, see [README.md](README.md); for the message-by-message network reference, see [SYNCING.md](SYNCING.md); coding agents should start with [AGENTS.md](AGENTS.md).

This document records current design intent and historical client observations. It is not an API contract, and some client-specific notes can become stale as Anniversary builds change. Verify uncertain behavior against the current code and client.

Large WoW addon (TBC 2.5.5 Anniversary) for managing raid assignments, roles, and buffs.

## Tech Stack
**In use:** Lua 5.1 (WoW Classic API) · AceGUI-3.0 + custom `CreateFrame` chrome (WdwFrame.lua) + modern Menu API (right-click) · AceAddon/AceConsole/AceDB-3.0 · LibClassicInspector (+LibDetours) for talent sync — caches in-range/peer talents, we consume `TALENTS_READY`; can't fetch, so out-of-range non-users stay unknown · AceComm-3.0 + LibSerialize + LibDeflate (copied from the user's WeakAuras) for the assignment sync layer (Sync.lua) · LibCustomGlow-1.0 (copied from NovaConsumesHelper) for the buffing bar's per-button glow.

## Coding Guidelines
* **Never edit `Libs/`** — treat all bundled libs as read-only; customize via overlays/wrappers/subclassing, never patch.
* **Logging:** verbose dev logs via `WhoDoesWhat:Print(...)`.
* **Class/spec metadata:** always from `WhoDoesWhat.Classes` (Data.lua).

## Features
* **Role & buff data (Data.lua):** all TBC classes/specs (icons, colors), collapsed categories, per-role default paladin buff priorities and default bans (backfilled to a full 6-buff order plus an `allowedCount` divider), custom roles. DB stores only deviations; `GetEffectiveBuffSetup` feeds the editor and `GetEffectiveBuffOrder` returns only the allowed prefix for assignment math. `PaladinBuffs`/`CCSpells`/`WarlockCurses` use TBC max-rank spellIds with Classic Era overrides in `ClientFeatures.lua`; Classic also adds Curse of Shadow. Wrong ids surface as "?" (CC icons via `GetSpellIcon`). `RaidTargetMarkers` skull-first; chat tokens = lowercased marker names.
* **Hunter pets (`hunter_pets` pseudo-role):** NOT assignable or customizable — removed from the Hunter role/category lists (no Set Role menu, Raider Roles dropdown, or Role Preferences page offers it; a one-off Core.lua migration clears old assignments + its customization). Registered by hand in `RolesAndCategories` (like Non-raider) so stale synced assignments still resolve. Instead every hunter automatically contributes one virtual pet (`GetPetMembers` in Assignments.lua, exported on `Assign`): `"<Hunter>'s Pet"` entries (apostrophe can't collide with character names; `owner`+`isPet` fields) that live only in the paladin-buff math — demand votes + own `ComputeBuffGrid` rows wanting `HunterPetBuffOrder = {might, kings, light}` from Data.lua (deliberately NOT backfilled, so a fully covered pet shows an empty cell). Non-raider hunters contribute no pet. In the buff grid the pets form their own section immediately after Warriors; they retain Hunter metadata/colors and use the pet role icon. Hunter pets ride the **Warrior blessing group** — a Greater Blessing on a Warrior reaches them (PallyPower files pets under Warrior for this reason). The shared plan first inherits matching Warrior Greaters, then exactly matches uncovered pet wants across the remaining paladins as individual **Normal** blessings. `PallyPowerBridge` and `GetPaladinBuffJobs` consume that same plan and Warrior Greater decision; unresolved real pet names and fake hunters' pets cannot become castable individual targets.
* **Buff tracking (BuffTracking.lua):** live scan of which paladin blessings are actually active on each group member **and hunter pet**, matched by localized aura name (rank-proof, Greater or Normal). Modern `C_UnitAuras.GetBuffDataByIndex` (indexed `UnitBuff` fallback), per-unit on `UNIT_AURA` + a 3s full-group backstop poll. In Classic the aura LIST is available at any range for group members (only durations go stale), so missing-buff detection works raid-wide; dead/offline still read as missing. Pets scanned via `raidNpet`/`pet` and keyed `"<Owner>'s Pet"` to match the plan (hunters only; pet changes ride the poll, not `UNIT_AURA`). API: `WhoDoesWhat:HasBuff(name,key)` → true/false/nil (nil = unknown/unscanned), `GetActiveBuffs`. `RefreshBuffingGridView` is the shared "buff plan changed" hook (every mutation site already calls it) — it repaints the grid AND the buffing bar; the grid red-flags planned cells whose raider lacks the blessing.
* **Paladin Buffing Bar (PaladinBuffingBarView.lua):** a movable, Nova-style **secure** bar — a clickable alternative to PallyPower that casts blessings directly (works with or without PallyPower installed). One button per CLASS the local paladin is assigned, from `GetPaladinBuffJobs` (on `Assign`), which collapses the buff grid into a class Greater (majority blessing) + per-player Normal exceptions, PallyPower-independent. **Left-click** casts the class Greater on a member (rotates through all resolvable members for range robustness); **right-click** cycles every assigned member's planned Lesser Blessing, including recipients of the class Greater, ordered missing first and then by shortest remaining duration. Secure `Execute`/`WrapScript` rotation (PallyPower's proven pattern, snippet branches on `button`) is baked out of combat and rebaked on `PLAYER_REGEN_ENABLED`; cast targets are unit tokens (`[@raid5]`/`[@raid5pet]`). Existing class buttons still repaint their effective job, `buffed/total` count, range state, and glow in combat; protected spell/target attributes and any added/removed class-button layout wait for `PLAYER_REGEN_ENABLED`. **Hunter pets bucket under the Warrior button** — a Greater on a Warrior reaches hunter pets, so a pet whose want matches the class Greater is covered for free; right-click can still top the pet up with its planned Lesser (real pet unit via `GetPetUnitInfo`). A pets-only bucket shows the pet icon, while a mixed one shows the class icon + a small pet badge. Per-button count comes from `HasBuff`, the icon greys when nothing's castable in range, and LibCustomGlow PixelGlow marks a reachable missing member. Alt-drag to move, left/right growth, "WDW Buffs" title. Local `settings.buffingBar*`: master toggle + a Developer "preview as any real/fake paladin" dropdown; fake-raid pets show grouped but aren't castable (no real unit).
* **Talent sync (TalentScanning.lua):** `TALENTS_READY` → `AutoAssignDetectedRole`: fill empty, follow respec, never fight manual override on unchanged spec (compare `db.profile.talentSpecs`). A client's FIRST detection (`talentSpecs` nil) never overrides an existing assignment — it may be manual or synced from a client that could inspect in range; without this, two clients with different caches tug a player between roles. **Single-writer Blizzard flags:** the Blizzard role flag (`UnitSetRole`) has no range check, so only ONE client — the group LEADER (`CanSetOthersBlizzardRole` in Core.lua; falls back to raid-assist only when no leader owns the board — BG / addonless leader, per `PermissionsOpenReason`) — ever writes OTHER members' flags; your own is always yours. A non-leader that detects a spec still saves + syncs the WDW assignment, and the leader applies the one `UnitSetRole` when it receives the board (`ReconcileBlizzardRoles`, the sole other-member flag write path — called from own edits, `Sync.ApplyState`/`ROLE`, the roster sweep, and `PLAYER_REGEN_ENABLED`). This stops several assists from racing `UnitSetRole` on one player from range. `UnitSetRole` everywhere only fires when the flag actually differs (re-setting an identical flag re-announces to the group and fights other role addons). Quiet (no announce). **Combat:** patch 2.5.6 protects `UnitSetRole` and `RaidFrame:Show` from addon execution, so role writes and the tank promote window are deferred until `PLAYER_REGEN_ENABLED`. Undetectable roles (warlock_firetank, druid_dreamstate, feral tank, customs) untouched. Flags: `LOG_TALENTS`/`LOG_TALENT_COMMS`.
* **Paladin buff-talent scan:** per-paladin ranks — Improved Might (0-5), Improved Wisdom (0-2), Kings (0-1), Sanctuary (0-1); Kings/Sanctuary are talent-GRANTED (untalented can't cast). Stored in `db.profile.paladinBuffTalents` (nil = unscanned, ≠ rank 0). Ranks read from the client's **native `GetTalentInfo`** matched by hard-coded `(tab, tier, column)` — NOT the library's positional cache, whose index order is shuffled on the Anniversary client (LibClassicInspector assumes native order == its static table; it isn't, so its ranks land under the wrong talent). Only reads on a fresh inspect (`isInspect`) or the local player — a cache replay/broadcast has no live native data, so it's skipped rather than zeroed. `active` spec only (via `GetActiveTalentGroup(isInspect)`), which is what they can cast now. Versioned wipe: `buffTalentScanVersion`.
* **Kick/reinvite catch:** `TALENTS_READY` fires only on data arrival, so rejoiners sit stale; debounced `GROUP_ROSTER_UPDATE` sweep replays from cache (cache-time gated) + `ReconcileBlizzardRoles` re-applies drifted role flags (leader-only for others; see the single-writer note above).
* **Local-player self-scan:** the library never fires `TALENTS_READY` for the player, so a `selfSync` frame replays the pipeline for our own GUID on `PLAYER_ENTERING_WORLD` / `CHARACTER_POINTS_CHANGED` / `PLAYER_TALENT_UPDATE` / `ACTIVE_TALENT_GROUP_CHANGED` (dual-spec swap changes castable blessings). Last two `pcall`-guarded (not on every build).
* **Assignment model (Assignments.lua):** on `WhoDoesWhat.Assign`. Section defs are MODEL-ONLY vocabulary (key/title/store/noun/whisperLead/spells/targetPlayer/autoRows/multiMarker/GetWarning — view-only flags were removed when the sections were hard-coded into Views/Sections/), `SectionByKey`, `GetEligibleMembers` (Developer Mode lifts filter) / `MembersOfClass` (strict), marker/spell/target text (`{skull}` tokens vs words), whisper collectors (named per section: `CollectTankWhispers` etc., generic ones kept for future sections) + `MassWhisper` (0.25s stagger vs throttle), `ComputeBuffGrid`/`ComputePaladinBuffSummary`/`CompileBuffRules` (derived paladin coverage + custom rules — see below), `AutoAssignWarlockCurses`/`ClearTankAssignments`/`ClearMisdirectAssignments` (exported for the views' header buttons), `PruneDepartedAssignments`, `SetAssignment` (exclusivity + pairWith + repaint; curses only now).
* **Main window (/wdw):** two scrollable columns. Both dimensions track the view mode in `ApplyViewMode`: full board = `FRAME_W` 940 wide (the two-column board needs ~890px content); Paladin-only narrows to `NARROW_FRAME_W` 470 (~the section box + the four-button top row floor), hides the permission strip so it can't collide with the buttons, drops the scrollbar (`scrollBarHideable` + reclaims its reserved width by anchoring the scroll to `-MARGIN`) and centers the lone box (`f.columns[COL_LEFT].x` offset). Height auto-fits the visible content each refresh (`f.scrollTop + content height`, clamped to `MIN_FRAME_H`..`MAX_FRAME_H` 130..550) so Paladin-only view is a short low-profile window and the full board grows until it scrolls. Boxes anchor-chained within their column (height change ripples only that column). Uneven: `LEFT_COLUMN_W` 378 (narrow — PaladinBuffs/WarlockCurses), right ~500 (Tank + busy dynamic rows — CC/Misdirect + future custom sections). Scroll child needs explicit `SetPoint`. `RefreshMainAssignmentsView()` repaints externally. Sections are hard-coded (see Views/Sections/ in Files); the bullets below describe each section's behavior. **Paladin-only view:** local `settings.paladinOnlyView`, controlled only by the main-window "Full view" checkbox, hides every section box but Paladin Buffs regardless of assignment state. `RefreshAll` ends with `ApplyViewMode` (box `SetShown` → `K.LayoutColumnBoxes` re-anchors visible boxes per column, skipping hidden → `K.UpdateContentHeight` ignores hidden boxes) then `UpdateViewToggle`.
  * **Dynamic row sections** (Tank, CC, and Misdirect in the right/wide column): pooled rows `[player] ([spell]) -> [marker] [edit] (!) [x] [mail]`; CC rows added via the header's "Add (+)" (title strip, not bottom); tank + misdirect rows are auto-managed (`autoRows`, below). Header buttons are row-button-sized (22px, -2 gaps) so header mail/X align with the rows' mail/x columns; title strip tightened (`SECTION_TITLE_H` 22, divider at -28, rows start -30). CC entry: `{player, marker=1..8|"all"|"custom", custom, spell}`; tank entry: `{player, markers={mix of 1..8|"all"|"custom"}, custom}` (array, kept skull-first by `NormalizeMarkers`).
    * Tank (`tankAssignments`, `autoRows`+`multiMarker`): **one row per marked tank, auto-managed** like misdirects — fixed player label and no Add. `EnsureAutoRows` runs during talent scans, direct role changes, and debounced roster lifecycle reconciliation; section refreshes only render, so opening the window cannot mutate or sync the board. The marker dropdown is a **multi-select** (incl. "Everything else"/Custom) so one tank holds all their markers on one row; selecting a new option closes the menu, while deselecting a checked option keeps it open. Toggles route through `SetTankMarkerPlayer`/`RemoveTankMarker` (one tank per marker — checking steals the value off its holder; misdirect sync + adoption ride along). Each row's **[x]** clears that tank's markers/custom text without removing the auto row. `KeepStray` keeps rows for marker-holding players who aren't marked tanks (unit-menu assignments) so they warn instead of vanishing. Warns unmarked player / empty markers. Header **[x]** (confirm popup `WHODOESWHAT_CLEAR_SECTION`) wipes all tank assignments; auto rows immediately repopulate with empty/default dropdowns and inherited misdirect markers clear.
    * CC (`ccAssignments`): spell dropdown from `CCSpells` filtered to assignee's class (full list while unassigned); incompatible reassign clears spell.
    * Misdirect (`mdAssignments`, `targetPlayer`, `autoRows="Hunter"`): **one row per hunter, auto-managed** — no Add/per-row [x]; `EnsureAutoRows` reconciles the store to the roster (retained rows keep their order + tank/marker, newcomers append, departed drop) in the model's debounced roster lifecycle handler, gated on edit permission (read-only clients render the leader's synced rows). Shared by the tank section via `autoRoster` (marked tanks) + `KeepStray`. Header **[x]** clears all assignments and immediately repopulates one blank row per hunter. The hunter column is a fixed label, not a picker; you only fill in each hunter's tank. Tank + marker: marker inherits the tank's first tank-marker — defaulted on tank pick (`FirstTankMarker`) and re-synced whenever that tank's markers are (re)assigned (`SyncMisdirectsForTank`, called from every tank-row change + the unit-menu tank setters), still hand-overridable via the row dropdown. Reverse too: assigning a tank to a marker adopts any tank-less misdirect already sitting on that marker (`AdoptMisdirectsForMarker`, empty targets only — never steals). Warns non-hunter/multi-misdirect/unmarked tank/tank-with-no-marker/marker-the-tank-isn't-tanking.
    * CC header: "X" clear-all behind `StaticPopup` (`WHODOESWHAT_CLEAR_SECTION`, `preferredIndex=3`); disabled when empty.
  * **Static sections (left/narrow column, `Sections`):** "Paladin Buffs" (computed summary, see next) and "Warlocks" (Improved Healthstone rank summary followed by the flavor's raid curses, mutually exclusive via `exclusiveWith`; TBC Elements floats for Affliction/Malediction, while Classic adds Shadow). Healthstone ranks are scanned natively at Demonology row 1 / column 1, display confirmed counts for ranks 2/1/0, and remain unknown until inspected or received from that warlock. The whole section disables with no warlocks. Dropdowns float preferred above divider. Every assignment dropdown (options + collapsed selected value) prefixes the player with their role's spec icon (`RoleIconMarkup`/`PlayerTextWithRole`; "" when roleless).
  * **Paladin Buffs section (`paladinSummary`):** NO assignment — blessings are never stored per paladin; coverage is derived (`ComputeBuffGrid`). One pooled read-only 24px row per paladin: `[role icon] Name  [buff] (n) > [buff] (n)`, up to 3 buffs each (count-desc, canonical ties), paladins sorted by total workload desc (`ComputePaladinBuffSummary`). Header mail whispers each paladin "Blessings: Might x12, Kings x3" (`CollectPaladinBuffWhispers`), with "Buffing Grid" beside it. A second "Buffing Rules" header owns "Add (+)" and an immediate clear-all X (both hidden in board view-only mode), and shows "No rules exist" when empty; PallyPower controls remain in the footer. Section grays with no paladins (`disableWhenNoClass`); box resizes + ripples its column.
* **Buff rules (`paladinBuffRules`, "Buffing Rules" > "Add (+)"):** editable rows under the summary — `[buff v] [Is Ignored / Prioritized for / Preferred by v] [target v] [x]`, one rule per blessing, max 6 (buff dropdown offers only unruled blessings; new rules start as inert "Preferred by (choose)"). Ignore = buff drops from the plan entirely; Prioritize (Everyone / Tanks-Healers-DPS / class → level-2 "All class"+roles) = buff jumps to front of matching raiders' orders AND their demand votes (`RuleAdjustedOrder`); Prefer by paladin = hard primary lock (+100 in the matcher, beats any rank gap — position still dominates so unwanted buffs aren't force-fed; lock also removes paladin+buff from the primary demand race). Prefer's paladin dropdown floats capable casters (known talent rank > 0) above a divider and annotates everyone — (talented)/(can't cast) for Kings/Sanctuary, (n/max) for Might/Wisdom, (not scanned) — and a row (!) warns when the named paladin has a known 0 in the buff's talent (gated: rule inert; Improved: blessing unimproved). Shared as `STATE.paladinStrategy`, permission-gated like the assignment board, cleared on group leave, and automatically pruned by the leader when a preferred paladin departs.
  * **Auto-assign:** Warlock only — TBC puts Elements on Affliction (else first) and Recklessness on a second warlock; Classic fills Recklessness, Elements, then Shadow on distinct warlocks. Settings gate the magic curses and Recklessness separately.
  * **Mail:** per-row whisper of full job list (disabled while unassigned); header mass-mail whispers all assigned (self filtered). Whispers use marker tokens; `:Print()` uses words (`AddMessage` won't expand tokens).
* **Buffing Grid (BuffingGridView.lua):** the former Raid Buff Grid and Paladin Full Grid are one no-scroll window. Each block starts with icon-headed Mark, Fortitude, Intellect, and Food status columns, followed after a visual gap by one 26px planned-blessing column per paladin; provider-class columns hide when that class has no active raider, and virtual hunter-pet rows leave raid-buff cells blank. Header tooltips describe each raid buff; Mark/Fortitude also list every provider's scanned improved-talent rank and offline state. A confirmed lower-rank Mark/Fortitude cell becomes a warning icon when a connected provider has a strictly better scanned rank. The window sizes to its content, and ≥20 raiders split into balanced side-by-side blocks. Paladin headers keep their role icon, outlined initial, and `RaiderTooltipView`. Disconnected rows use shared gray styling, Paladin assignment cells hide, and raid-buff cells retain unavailable-state tooltips. The title-bar **Rescan** button calls `RescanBuffingTalents` for reachable Paladins, Priests, and Druids. Planned blessing cells use `ComputeBuffGrid`; confirmed missing blessings are desaturated behind a red border, while missing raid buffs use the ready-check X. Paladin coverage remains derived per raider from roster, roles, talents, and rules through the exact matcher; nothing is stored in the view.
* **PallyPower bridge (PallyPowerBridge.lua):** `SyncToPallyPower` maps the computed grid onto PallyPower's model (one Greater Blessing per class per paladin; minority raiders become Normal-blessing exceptions), updates a co-installed PallyPower's local tables when present, and broadcasts its wire protocol (CLEAR SKIP → PASSIGN per paladin → batched NASSIGN). Without PallyPower installed, WDW sends the protocol directly and uses its observed-board mirror for Diff/Fix status and minimal role-change pushes. Receivers only accept assignments for others from a leader/assist sender (or Free Assignment) — button warns without that authority. Fake-raid names never hit the wire. **No auto full-resync or diff-window popup** — a paladin joining/leaving or turning Non-raider reshapes the whole grid but touches nothing in PallyPower, so the passive assignment/status UI surfaces real coverage drift through `CheckPallyPowerSync`; users open the formatted **PallyPower Differences** window manually when they want the details. The check compares each active target's effective blessing after Normal overrides, not the raw Greater/Normal table shape, because multiple layouts can provide identical coverage. `PushPlayerBuffToPallyPower(name, priorDiffs)` is the minimal role-swap path: from an aligned baseline, if only that raider's effective blessings change, it sends only their NASSIGN rows (including `0` clears). Pre-existing effective drift or changes to other raiders leave PallyPower untouched for the passive UI to report. PallyPower-authorized leaders/assists send directly; ordinary-raider role changes are relayed once the WDW leader receives their synced role. Minimal NASSIGN changes parse in combat; PallyPower defers protected layout work until combat ends. While session logging is enabled, PLPWR traffic lands in `WhoDoesWhat.PallyPowerLog`, translated for `/wdw pplog`; logging resets off on reload.
* **Curse calculator (CurseCalculatorView.lua):** pulls a fight from Details!, prefers its recorded boss target with the prior max-damage fallback, and estimates raid damage provided (or foregone) by the flavor's curses. Classic splits CoE (Fire/Frost, optional 1.21x Ignite double-dip) from CoS (Shadow/Arcane), uses level-60 armor math/ranks/presets, and omits Malediction/Blood Frenzy; TBC retains combined-school CoE, Malediction, level-70 armor values, and Blood Frenzy. CoR reconstructs armor from user-ticked debuff assumptions, excludes known bleeds via spell-id list, and accepts optional average flat armor penetration. All estimates assume 100% uptime and deliberately do not value resistance reduction.
* **Raider Roles (RaiderRolesView.lua):** members shown in four borderless Tanks/Healers/DPS/No Role grids (counts in headers), with alternating class-tinted rows from `Data.lua`, class-then-name sorting, a WDW-status column, and a left-aligned per-row role dropdown (permission-gated for others, own row always live) + (!) while roleless/deleted-custom. Dropdown mirrors the unit menu's Set Role exactly: class + custom roles, then a divider + **Non-raider** (`SetAssignedRole` with `NON_RAIDER_ROLE_ID`; shows the zzz icon, no warning, lands in the No Role bucket since `wowRole=false`), and a passive disabled "None" shown only while roleless — neither panel un-assigns a role back to roleless. Left-hand row icon = the assigned role's spec icon, falling back to the class icon when roleless/unresolved. Disconnected raiders use the shared alternating gray row colors, a gray name, desaturated role icon/dropdown, and the shared warning icon in the WDW column; `UNIT_CONNECTION` refreshes this live.
* **Settings (AddonSettingsView.lua):** General → Announce Role Changes (`settings.announceRoleChanges`, default on — gates the "[WhoDoesWhat] X was changed to..." group message in `SetAssignedRole`; Log Operations and Blizzard's own role-flag message are unaffected). Developer Mode (lifts class filters, keeps gated sections live, opts out of CC auto-clear; warnings still fire) + Log UI Updates (persisted → `LOG_UI_BUILDING`) + Log Operations (persisted → `LOG_OPERATIONS`; gates routine assignment, reset, auto-assign, role, customization, whisper, PallyPower-success, and manual-sync-success messages while leaving warnings and no-op explanations visible) + Populate Fake Raid.
* **Populate Fake Raid (FakeRaid.lua):** testing toggle (`settings.populateFakeRaid`) that appends `FakeRaid.ROSTER` (always 23 fakes: 3 tanks, 5 healers, DPS fill) at the single roster choke point `GetEligibleMembers`. `Rebuild()` assembles the roster deterministically (no randomness — identical on every client) from CORE + the first `settings.fakeRaidPaladinCount` (1–4, settings dropdown) of PALADINS (prot Kings+Sanct → ret Might5 → holy Wisdom2 → ret Might5+Wisdom2, the overlap exercising auto-assign tie-breaking) + a substitute resto shaman while Holy is out (count<3) + DPS_POOL in fill order. Count changes while live wipe the board and clear every possible fake name (`EachPossibleFake`, superset — the current roster may no longer include an old name) before re-injecting. Fakes' roles → `db.profile.assignments`, paladins' ranks → `db.profile.paladinBuffTalents`, and warlocks' Healthstone ranks → `db.profile.warlockHealthstoneTalents`, keyed by name, so the views treat them like real scans; local player is the 24th seat. `SetFakeRaidEnabled` wipes the board (raid/tank/CC/MD) on **both** transitions and adds/removes every fake trace. `ReapplyFakeRaid` re-writes the fakes' roles/talents while the toggle is on — called from OnInitialize and after Sync's group-leave board wipe (which can fire around reload/logout while solo and would otherwise eat them; re-inject sits before the wipe path's `Fingerprint()` refresh so it never reads as a local edit). Solo-testing tool — not guarded against broadcasting into a real group's sync.
* **All Roles ("Role Preferences"):** two-column class list, expand specs/categories, gear marker on customized, "+ Create Custom Role".
* **Single-role customizer:** full buff priority reorder around an `END` divider (rows below it are banned; Down on the last allowed row bans it, Up on any banned row promotes it), 3 modes (built-in/custom/create), role dropdown (Blizzard micro role atlas), dirty status, Save/Apply/Reset/Delete.
* **Unit menu (UnitMenuExtensions.lua):** `Menu.ModifyMenu` on self/player/target/party/raid. "Set Role" pop-out (persists, sets role flag, announces); tank-marker grid (multi-select; checking moves the marker onto that tank's row, unchecking clears just the marker — rows are roster-managed), CC target grid, misdirect pop-outs mapping onto stored rows (overwrite covering row or create; one sheep/mage, one tank/hunter). Below a divider: **Non-raider** (`non_raider`, Data.lua) — classless pseudo-role for anyone sitting out; its pseudo-class lives outside `Classes` so Role Preferences never lists it. Non-raiders drop out of buff demand votes, class-filtered rosters (buff/curse dropdowns + pools; `GetEligibleMembers` filters them on any class-filtered query), and the buff grid; marking someone Non-raider clears any paladin-buff rows (and override locks) they held.
* **Main-tank promote (RaidMenuExtensions.lua):** `SetPartyAssignment("MAINTANK",...)` is PROTECTED — can't promote (demote via `ClearPartyAssignment` works, auto for non-tanks). Instead, play the raid-warning sound and bounce an arrow at the player's row after the leader opens Blizzard's Raid tab; `GROUP_ROSTER_UPDATE` cleans up on success. **Multi-tank:** several tanks can be pending at once (`pendingPromotes` set + pooled per-name arrow/glow highlights). Pending entries clear when promoted, no longer tanks, or departed. The addon never calls `ToggleFriendsFrame`, `RaidFrame_LoadUI`, or `HideUIPanel`: current 2.5.6 builds can carry addon taint from an otherwise-allowed out-of-combat panel open into a later native in-combat `RaidFrame:Show`. A lightweight poll notices when the leader opens the Raid tab. Highlights stay parented to `UIParent` and only anchor visually to `RaidGroupButtonN`; reparenting addon frames into that protected hierarchy also risks taint. `StartPromoteWatch` is idempotent per player. Only the flag-authority (leader, `CanSetOthersBlizzardRole`) raises arrows — from a direct tank-role set (`SyncBlizzardRoleState`) or the first-scan sweep in `OnTalentsReady` (any WDW-tank not yet MAINTANK).
* **Feral tank detection:** cat DPS and bear tank share the Feral Combat tree, so `SPEC_ROLES` can only guess `druid_feral_dps`. `OnTalentsReady` upgrades the guess to `druid_feral_tank` when the player already reads as a tank — holds the WDW feral-tank role, is flagged `TANK` (`UnitGroupRolesAssigned`), or is a promoted MAINTANK — so a bear that joined pre-flagged as tank isn't detected as DPS and doesn't get its TANK flag stomped.
* **Group messaging:** `WhoDoesWhat:SendGroupMessage(msg)` — RAID/PARTY/silent solo.
* **Editing permissions (Permissions.lua):** raid-only (party/solo always open); rule stands down wholesale (free-assign, gray note says why) in battlegrounds (`IsInInstance()=="pvp"`; sync uses INSTANCE_CHAT there) and when the current leader isn't known to run WDW (`LeaderRunsAddon` checks `syncPeers` — every comm sender Sync hears from, session-only, never wiped; leaderless moments err open; checked live so leadership changes take effect at once); the RAID LEADER picks who edits the board: `leader` / `assistant` (one named player) / `assists` (default — matches the old assist-gating) / `everyone`; leader always may. Setting lives in `db.profile.permissions {mode, assistant}`, rides the sync snapshot, resets to default on group leave. Enforcement is layered: `RequireEditPermission()` backstops every Set\* API (incl. `SetAssignedRole` for others; own role ALWAYS settable — `CanEditRoleOf`), `PruneDepartedAssignments` no-ops read-only, Sync gates broadcasts both ways. `PlayerCanEditAssignments(name)` ranks via `GetRaidRosterInfo`. UI: main view renders read-only without rights — dropdowns swap to plain-text lines (`row.roText`; class colors survive, unlike gray disabled dropdowns), \[+]/\[x]/clear-all/custom-editbox/mail (row + header) hidden, Auto greyed (not hidden) with a permission tooltip that survives the class-disable pass, warnings (except on unassigned rows — a to-do a viewer can't do) + demand + Grid/Info/Calc pop-outs stay, header buttons re-anchor right-aligned around hidden ones (`LayoutHeaderChain`, rightmost-first chains) and text buttons size to their labels; leader gets an "Editing:" picker dropdown top-left (level-2 assistant list via `UIDROPDOWNMENU_MENU_VALUE`), others a gray note naming the rule. Unit menu: pop-outs (tank/CC/MD) require permission, otherwise replaced by gray read-only summary lines of that player's assignments; own Set Role stays live. RaiderRolesView dropdowns permission-gated the same way.
* **Assignment sync (Sync.lua, AceAddon module "Sync"):** whole-board sync between WDW users in a group. Syncs roles (`assignments`), tank/CC/misdirect rows, and non-paladin static rows (warlock curses); **paladin buff rows deliberately excluded for now** — instead each paladin broadcasts their own 4 buff-talent ranks and each warlock broadcasts their own Improved Healthstone rank (read natively on the sender) into receivers' local talent caches. A join/reload client's initial HELLO also carries only its three talent-tree totals, letting every WDW peer immediately run the existing class/tab role inference; LibClassicInspector remains the ongoing full-talent source. A fresh direct inspection of another roster member can additionally send a deduplicated `OBSERVE` with the target's three totals and exact relevant utility ranks; any raider may contribute this evidence, receivers validate it against their roster and infer the role themselves, and the leader relays accumulated non-WDW observations to later joiners. Conflict model: leave group → whole board wiped incl. permissions (talent caches survive); join group → a compatible leader is the source of truth (joiner HELLOs, ordinary peers stay silent, leader whispers the full snapshot plus its current peer/version/utility-rank directory, applied unconditionally + popup if it overwrote a non-empty board, 5s timeout keeps local if no compatible leader answers); mid-group any PERMITTED member's edit broadcasts the full snapshot (permissions ride the snapshot; receivers reject STATE from unpermitted senders by their own current belief), last-write-wins with a Lamport rev + sender-name tiebreak so simultaneous edits converge. Unpermitted clients pin their fingerprint each poll (local drift never broadcasts, even after a later promotion) and push own-role changes over a dedicated `ROLE` message everyone accepts (own role only, `lastOwnRoleSent` stops apply-echo); `OBSERVE` is evidence, not a board edit, so it is permission-independent. `PLAYER_ENTERING_WORLD` (+3s; roster unreliable at fire time) re-runs the handshake — members redo the HELLO pull; the leader announces with a STATE broadcast and, once per cold session, requests one group RANKS/VERSION announcement per peer to rebuild the ephemeral directory for everyone — because reload/login wipe `syncPeers` and `GROUP_JOINED` doesn't fire then. Rev is wall-clock-seeded (`max(rev+1, GetServerTime())`): a plain counter reset to 0 on reload and every fresh-session broadcast lost to the old session's higher revs. Change detection = 2s fingerprint poll of the synced slice (write paths are too scattered to hook; view dropdowns mutate entries in place via a local repaint). Applying a remote board updates the fingerprint first so it never echoes back. `/wdw sync` = manual push (leader) / pull (member). `WhoDoesWhat.LOG_SYNC` chat-logs traffic. Protocol versioned (`PROTOCOL`); mismatches warn once and ignore each other.
* **Shared paladin strategy:** `Snapshot()` exposes `db.profile.paladinBuffRules` as `state.paladinStrategy`; it participates in the board fingerprint, leader join replacement, revisions, and permission-gated editing. It is cleared on group leave. `PruneDepartedAssignments()` also removes `prefer` rules whose named paladin left; the existing debounced roster lifecycle elects the leader as the sole housekeeping writer, so views remain read-only renderers and the normal fingerprint poll sends one resulting `STATE`.
* **DB shape (Core.lua):** `assignments` (name→role), `talentSpecs`, `paladinBuffTalents` (+`buffTalentScanVersion`), `warlockHealthstoneTalents`, `raidAssignments` (row id→name), `paladinBuffRules`, `tankAssignments` (one row per tank: `{player, markers={...}, custom}`; a one-off OnInitialize migration merges the old one-row-per-marker shape by player; Sync's `PROTOCOL` is 7)/`ccAssignments`/`mdAssignments`, `roleCustomizations` (`{buffOrder, allowedCount}`; missing counts are legacy-compatible), `customRoles` (+counter), `permissions` (mode + assistant), `settings`.

* **Addon version discovery:** `Core.lua` reads `WhoDoesWhat.VERSION` from TOC metadata and every Sync message carries it. With a compatible WDW leader, ordinary HELLO receivers stay silent and the leader's initial STATE includes its current peer/version/utility-rank directory. A cold leader reload requests one group RANKS or VERSION announcement per peer to rebuild that ephemeral directory for everyone. Without a compatible leader, stable peers retain the old RANKS/VERSION whisper fallback so presence remains discoverable; clients which are themselves awaiting reload sync stay silent to prevent mutual fanout. The main title shows the standard warning icon when a current group member reports a higher numeric version. In unpackaged source only, Developer → Simulate newer addon version makes that client display, advertise, and compare as the next patch version so a current-version peer sees the out-of-date warning. Every simulator entry point is inside BigWigs `--@do-not-package@` blocks and is removed from release archives.

## Releases (CurseForge automatic packaging)
* A GitHub push webhook feeds the CurseForge packager, configured to package **tagged commits only** — pushes to `main` are free, a release happens only when a tag lands.
* To cut a release: commit, then `git tag 1.0.5 && git push origin 1.0.5`.
* Tag text becomes the packaged `## Version:` through `@project-version@`. Use plain `1.0.5`, **no `v` prefix**. A tag containing `beta`/`alpha` (for example `1.1.0-beta`) packages as a Beta/Alpha build instead of a Release.
* Before the release commit, set the TOC debug block's literal `## Version` to exactly the intended tag. The live main-window title and peer-version warning read that last active value; packaging comments the debug block and substitutes the tag into the earlier `@project-version@` line.
* Keep the version simulator inside `--@do-not-package@` blocks and confirm its setting name is absent from the generated release directory before tagging.
* `.pkgmeta` zips as `WhoDoesWhat/` and strips repo-only files (README.md, AGENTS.md, DEVELOPMENT.md, .vscode, .pkgmeta); `Libs/` ships as committed (no externals).
* `## Interface:` remains literal. CurseForge documents `@project-version@`, but does not document an equivalent token that discovers the current WoW Interface number. Revalidate and update the literal after relevant client patches.
* References: [CurseForge automatic packaging](https://support.curseforge.com/support/solutions/articles/9000197281) and the [BigWigs packager](https://github.com/BigWigsMods/packager).

## Historical client observations (revalidate before relying on them)
* The addon currently targets Interface `20505` for TBC Anniversary. Confirm the current client value after patches; an outdated value can mark the addon out of date.
* Modern Menu API exists: `Menu.ModifyMenu`, `MenuUtil.Create*` + `rootDescription:Insert(desc, index)`. Submenu parents need non-nil click callback.
* `SetPartyAssignment` protected (Blizzard-UI only); `ClearPartyAssignment` is callable. `UnitSetRole` is callable by addons only out of combat as of 2.5.6.
* Raid tab rows are `RaidGroupButton<i>` (i = roster index); `RaidGroup<g>Slot<s>` are empty slots. `Blizzard_RaidUI` is load-on-demand; do not load or open it from addon execution on current builds.
* LibClassicInspector's talent ranks are unreliable on Anniversary (2.5.x): native `GetTalentInfo(tab, i)` index order is unstable, but the lib reads its positional cache assuming static order → ranks land under the wrong talent. Read ranks from native `GetTalentInfo` matched by `(tier, column)` instead (only valid during the lib's inspect or for the local player). NovaRaidCompanion does the same (sorts by row/column).
* `TALENTS_READY` fires only on data arrival, never on roster changes — rejoiners need manual cache replay.
* `UIDropDownMenuTemplate`: ~15px transparent padding/side, label 7px from left / 43px from right — ~69px floor for icon-only box.
* Scroll children need explicit `SetPoint` or won't render until moved; sibling frames render in unstable order — set explicit `SetFrameLevel` on section boxes.
* Blizzard UI source: github.com/Gethe/wow-ui-source branch `classic_anniversary`.
